## P0-1 fix: ambiguous HTTP Content-Type cannot become a vendor close

The bounded Twelve Data/Massive daily-bar diagnostic previously parsed an HTTP 200 JSON-looking response even when the response had **no Content-Type**, an incompatible Content-Type, or duplicate Content-Type headers. This could count an ambiguous transport response as `VALID_VENDOR_BAR` in the *diagnostic* inventory (never as an official close). Implementation commit [47bf4dafa4c1500194074ae4e81d7e933e96b0ad](https://github.com/Dirtyhandgernades/Dudebot/commit/47bf4dafa4c1500194074ae4e81d7e933e96b0ad) requires exactly one explicit `application/json` media-type header (optional parameters such as `charset=utf-8` allowed), examines all header occurrences, and censors missing/contradictory/non-JSON declarations as `UNVERIFIED_JSON_CONTENT_TYPE` before JSON parsing. The raw bounded SHA-256 receipt fingerprint is retained for diagnostic integrity; no raw body, URL query credentials or arbitrary vendor headers are exposed. The same-run provider request budget stops on this ambiguous response, preserving missing original ticker/session slots.
